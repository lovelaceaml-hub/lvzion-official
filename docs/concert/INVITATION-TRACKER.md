# Concert Invitation Tracker — implementation draft
Owner-approved request: November 23, 2026. This branch is not a release and the SQL review draft has not been applied.

## What this draft adds
- Manager-only bottom-bar More menu → Invitation Tracker at the existing concert workspace (also #invitations).
- Named invite records from the active concert; sender identity grouped by stored sender email, group leader grouped by recorded label (unknown remains unknown), recipient name/email, Pacific creation and send timestamps, app delivery attempt count, RSVP and registration columns.
- Explicit test flag, audited marking/unmarking, default exclusion from the filtered metrics; no deletion or heuristic classification. Historical tests must be reviewed by the owner.
- A separate-registration hint requires matching event, normalized email and name, and an unclaimed active ticket. It does not automatically link or confirm an invitation.
- Manager resend of the same original link; checks active event, unconfirmed/unwithdrawn invitation, email, no possible separate registration, not a marked test, mail cooldown and existing transactional delivery claim. No automatic sends. Provider bounce, suppression or complaint disables UI resend; durable provider-based suppression at server remains a release requirement.
- Excel .xlsx export of filtered/group-ordered rows. Per AGENTS.md, exclude private addresses and signed links from exported files; recipient email remains visible to authorized managers in-app. No new packages.

## Provider lookup
Optional server-only LVZ_CONCERT_RESEND_READ_KEY. The lookup uses Resend list/retrieve endpoints, restricted to production, event sender and invitation subjects, and checks exact signed link in original message text/HTML before associating provider evidence. No message body, provider credentials or signed links are returned. Bounded to 3 pages / 30 candidates / 16 seconds; partial or unavailable is explicit. The provider last_event is a current observation, not a complete event history, and cannot establish a negative open result. Historical messages that cannot be matched exactly remain unverified. Open tracking depends on existing domain configuration; do not enable domain-wide tracking silently. For durable independent delivered/bounced/opened timestamps, implement verified Resend webhook and exact provider-message ID correlation (with replay protection), or obtain an approved provider event history endpoint. Never treat an SMTP accept as delivered. See https://resend.com/docs/api-reference/emails/list-emails and https://resend.com/docs/api-reference/emails/retrieve-email.
